# SaraSystem

> Generic education management platform combining LMS (learning), TMS (training management) and SIS (student information), for school chains, companies or language institutes. One installation serves one organization, and its schools/branches are tenants in a shared DB ([ADR 0002](docs/decisions/0002-tenancy-model.md)); never hard-code school-only assumptions. It is a redesign of the legacy **LMS** project at `/home/ali/Projects/LMS` (`../LMS`) — use it as read-only reference; never modify it unless asked.

This file is loaded into every agent session. Keep it short; details live in `docs/`.

## Commands

```bash
docker compose up -d                                   # app → http://localhost:8000, Vite 5174, PostgreSQL 5432
docker compose exec -u sail laravel.test php artisan …  # artisan (always as user sail, not root)
docker compose exec -u sail laravel.test php artisan test --parallel   # whole suite; single files/--filter without --parallel
docker compose exec -u sail laravel.test vendor/bin/pint  # code style
docker compose exec -u sail laravel.test npm run build    # or `npm run dev` for Vite HMR on :5174
```
The host has no PHP/Composer/Node; everything runs in the container.
Containers reach the internet only through the host VPN ([docker/vpn-proxy](docker/vpn-proxy/install.sh)). Install or change packages only when the user asks.

## Rules for agents

1. **Docs are part of the change.** When a task changes something a doc describes, update that doc in the same task. A task is not done until the docs match the code.
2. **Update `docs/progress.md`** at the end of every meaningful task: move items between Done / In progress / Next, add known issues you found.
3. **Record decisions.** When you (or the user) pick between real alternatives — library, data model, API shape, structure — add an ADR in `docs/decisions/` using `0000-template.md`, and link it from `architecture.md` if relevant.
4. **New domain term?** Add it to `docs/glossary.md`.
5. **Don't duplicate.** Docs explain *why* and *how things fit together*; don't copy what's obvious from the code. Prefer linking to files (`src/foo.ts`) over pasting code.
6. **Keep this file lean.** Only add here what every session needs; put the rest in `docs/`.
7. If the docs and the code disagree, trust the code, fix the doc, and mention it to the user.
8. **Never copy code from `../LMS` directly.** Port only the parts the user names, one part at a time. Review the LMS code first, then rewrite it for this stack and refactor where needed. See [conventions.md → Porting from LMS](docs/conventions.md#porting-from-lms).
9. **Commits:** when a piece of work reaches a sensible commit point, tell the user and propose a commit message (Conventional Commits, English). Commit only after the user approves.
10. **Modules:** business features go in `Modules/{Name}` (`module:make {Name} --inertia`); `app/` is only the platform core. See [conventions.md → Creating a module](docs/conventions.md#creating-a-module-adr-0005).
11. **Tenancy:** every tenant-owned model uses `BelongsToTenant`, and every tenant-owned feature has a cross-tenant isolation test. See [conventions.md → Tenancy rules](docs/conventions.md#tenancy-rules-see-adr-0002).
12. **Boost guidelines below** are generated by Laravel Boost (`php artisan boost:update`); don't edit inside `<laravel-boost-guidelines>` by hand. Where they conflict with the rules above, **these rules win**. In particular, keeping `docs/` updated is always required, and every `php artisan`/`composer`/`npm` command runs inside the container (see Commands).

# Inertia

- Inertia creates fully client-side rendered SPAs without modern SPA complexity, leveraging existing server-side patterns.
- Components live in `resources/js/Pages` (unless specified in `vite.config.js`). Use `Inertia::render()` for server-side routing instead of Blade views.
- ALWAYS use `search-docs` tool for version-specific Inertia documentation and updated code examples.
- IMPORTANT: Activate `inertia-vue-development` when working with Inertia Vue client-side patterns.

# Inertia v3

- Use all Inertia features from v1, v2, and v3. Check the documentation before making changes to ensure the correct approach.
- New v3 features: standalone HTTP requests (`useHttp` hook), optimistic updates with automatic rollback, layout props (`useLayoutProps` hook), instant visits, simplified SSR via `@inertiajs/vite` plugin, custom exception handling for error pages.
- Carried over from v2: deferred props, infinite scroll, merging props, polling, prefetching, once props, flash data.
- When using deferred props, add an empty state with a pulsing or animated skeleton.
- Axios has been removed. Use the built-in XHR client with interceptors, or install Axios separately if needed.
- `Inertia::lazy()` / `LazyProp` has been removed. Use `Inertia::optional()` instead.
- Prop types (`Inertia::optional()`, `Inertia::defer()`, `Inertia::merge()`) work inside nested arrays with dot-notation paths.
- SSR works automatically in Vite dev mode with `@inertiajs/vite` - no separate Node.js server needed during development.
- Event renames: `invalid` is now `httpException`, `exception` is now `networkError`.
- `router.cancel()` replaced by `router.cancelAll()`.
- The `future` configuration namespace has been removed - all v2 future options are now always enabled.
