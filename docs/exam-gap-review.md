# گزارش تطبیق ماژول Exam با معیارهای گفت‌وگو

**۱۰ نوامبر ۲۰۲۶ · مبنای بررسی: `f35e8cc`**

این گزارش [متن گفت‌وگوی ارائه‌شده](../test.txt) را با کد، فرم‌ها، مسیرهای HTTP و تست‌های Exam و اتصال آن به جلسات Class مقایسه می‌کند. گفت‌وگو هم فهرست قابلیت‌های ممکن را دارد و هم پیشنهادهای معماری؛ نبود هر قابلیت به‌خودی‌خود باگ نیست.

**نتیجه:** SaraSystem آزمون آنلاین فردی و آزمون جلسهٔ کلاس را از ساخت بانک تا تصحیح و نمایش نتیجه پوشش می‌دهد. بانک سؤال واقعاً قابل استفادهٔ مجدد است، اما هنوز مدل مالکیت، مجوز اشتراک، گردش تأیید و تحلیل سؤالِ پیشنهادشده در گفت‌وگو را ندارد. مهم‌ترین مشکلات فعلی، صحت ثبت تلاش بعدی، ثبات نتیجه، تعداد سؤال‌های تحویلی و زمان نمایش کلید پاسخ‌اند.

## بانک سؤال: تفاوت دقیق با مدل پیشنهادی

| معیار | وضعیت در SaraSystem |
|---|---|
| سؤال مستقل، استفادهٔ مجدد بدون کپی | **دارد.** یک رکورد سؤال با جدول واسط یکتا به چند بانکِ همان شعبه وصل می‌شود. آزمون به بانک ارجاع می‌دهد؛ کپی سؤال فقط برای ثبت چیزی است که یادگیرنده واقعاً دیده. تغییر سؤال در بانک‌ها مشترک است و بر شروع‌های بعدی اثر می‌گذارد. |
| یک بانک مالک + چند عضویت | **مالکیت ندارد.** مدل امروز همان رابطهٔ چندبه‌چند بدون بانک مالک است. فرم موقع ساخت/ویرایش حداقل یک بانک می‌خواهد، ولی حذف آخرین بانک می‌تواند سؤال را بدون بانک باقی بگذارد. حذف عضویت یک بانک، مادامی که خود سؤال حذف نشود، سؤال را از سایر بانک‌ها حذف نمی‌کند. |
| مجوز و مدیریت اشتراک | **سطح شعبه و نوع منبع دارد.** مجوزهایی مثل دیدن/ویرایش سؤال و بانک وجود دارند. نقش مالک، ویراستار، داور یا مصرف‌کننده در سطح بانک/عضویت، اشتراک موقت، ثبت اشتراک‌دهنده و حالت `live/snapshot` عضویت وجود ندارند. فیلتر بانک در فهرست سؤال‌ها کنترل دسترسیِ جدا برای هر بانک ایجاد نمی‌کند. این یک کمبود برای بانک محرمانه در همان شعبه است؛ شواهد، نشت بین شعبه‌ها را نشان نمی‌دهند. |
| اشتراک میان شعبه‌ها یا سازمان‌ها | **ندارد.** بانک و سؤال به شعبه محدودند. طبق [ADR 0002](decisions/0002-tenancy-model.md)، هر نصب برای یک سازمان است؛ بانک مرکزی مشترک میان شعبه‌ها می‌تواند نیاز پروژه باشد، اما اشتراک بین چند سازمان فرض دیگری است. |
| محتوا و متادیتا | **پایه.** شناسه، متن ساده، نوع، گزینه‌ها و کلید، بارم، فعال/غیرفعال و زمان ایجاد/ویرایش وجود دارند. عنوان/کد مستقل سؤال، رسانه/فرمول، توضیح و راهنما، نویسنده، منبع، زبان، سطح دشواری، بلوم، مبحث/تگ، دسته/زیردسته و سطح محرمانگی وجود ندارند. |
| چرخهٔ حیات | **فعال/غیرفعال.** فقط فعال‌ها برای تلاش جدید انتخاب می‌شوند؛ پیش‌نویس، بازبینی، تأیید، انتشار، آرشیو و بازنشستگی جدا ندارند. گردش تأیید سؤال وجود ندارد و سؤال جدید در فرم به‌طور پیش‌فرض فعال است. |
| نسخه‌بندی و ردگیری استفاده | **Snapshot تلاش دارد.** متن، نوع، ترتیب گزینه‌ها، کلید و بارمِ ارائه‌شده ذخیره می‌شوند. نسخهٔ تغییرناپذیر بانک، نسخهٔ قفل‌شده در زمان انتشار، تاریخچهٔ ویرایش و گزارش آمادهٔ استفاده بر حسب نسخه وجود ندارند. شناسهٔ سؤال در پاسخ تلاش ثبت می‌شود، اما با حذف سؤال از بین می‌رود. |

## ترتیب پیشنهادی کار

1. **صحت آزمون فعلی:** اتصال ذخیره/تحویل به شناسهٔ همان تلاش، کنترل سهمیه با در نظر گرفتن هم‌پوشانی بانک‌ها، ثابت نگه داشتن قواعد مؤثر بر نتیجه و تفکیک زمان انتشار پاسخ از سطح نمایش نتیجه.
2. **عملیات آزمون رسمی:** سیاست روشن پایان/ارفاق، بستن زمان‌بندی‌شدهٔ تلاش‌های رهاشده و آرشیو به‌جای حذف سوابق؛ سپس فریز کردن مجموعهٔ سؤال یا نسخه‌های مجاز برای آزمون‌هایی که باید محتوای ثابتی داشته باشند.
3. **بانک حرفه‌ای بر اساس نیاز محصول:** اگر چند مدرس یا شعبه باید سؤال‌های مشترک یا محرمانه داشته باشند، مالکیت بانک، مجوز عضویت و تاریخچهٔ تغییرات را طراحی کنید. اگر مشکل اصلی ساخت آزمون متوازن است، متادیتای مبحث/دشواری و Blueprint را جلوتر بیاورید. تحلیل سؤال و تبادل استاندارد را بر پایهٔ نیاز واقعی اولویت‌بندی کنید.

**اعتبارسنجی:** ۳۶ تست موجود Exam و اتصال جلسهٔ Class با ۳۷۲ بررسی پاس شدند. سه آزمایش موقت HTTP روی پایگاه دادهٔ تست با ۵۴ بررسی، ثبت دیررس، تغییر وضعیت قبولی پس از ویرایش و مشاهدهٔ کلید پیش از تلاش مجدد را بازتولید کردند. سایر یافته‌ها از بررسی کد و تست‌های موجود به دست آمده‌اند. آزمون بار یا اجرای مرورگر انجام نشد؛ کد برنامه و متن گفت‌وگو تغییر نکردند.
